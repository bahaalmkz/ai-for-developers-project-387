# Критерии ревью

Ревью проверяет изменения относительно спецификации и тикетов, а не стиль: форматирование и линтеры запускает `mise run check`, их вывод в ревью не повторяем. Каждое замечание — подтверждённый дефект: файл и строка, условие ошибки, последствие. Если подтверждённых дефектов нет, так и напиши.

## Занятость слотов

- Занятый слот не остаётся доступным для повторной записи.
- Запись на занятое время, в том числе частичное наложение встреч разной длительности, отклоняется с `409`; встреча не создаётся.
- Проверка занятости и вставка встречи выполняются в одной транзакции под блокировкой (`calendar_lock`, ADR 0004), поэтому два одновременных запроса не создают две встречи.

## Время и расписание

- Сетка стартов — 30 минут, окно записи — 14 дней, начиная с сегодняшнего.
- Сегодня доступны только слоты, которые ещё не начались.
- Расписание фиксировано: 09:00–18:00, слот целиком помещается до 18:00, часовой пояс `Asia/Almaty` (ADR 0003); владелец его не настраивает.
- В API время передаётся в ISO 8601 со смещением; гость видит время в часовом поясе владельца с подписью пояса.

## API и контракт

- API меняется только через `contract/main.tsp` → `contract/openapi.yaml` (`mise run contract`). `contract/openapi.yaml` и `frontend/src/api/generated/` руками не правятся.
- Ошибки API — единый формат `{code, message}`; ошибки полей добавляют `fieldErrors`.
- Новый маршрут или поле сначала появляются в контракте, затем в контроллере и клиенте; расхождение контракта и реализации — дефект.

## Данные

- Изменения схемы H2 совместимы со старыми данными (`backend/data/calendar`): существующие типы встреч и записи читаются после обновления.
- Миграция идемпотентна: повторный запуск не теряет и не дублирует данные.

## Тесты

- Основной и негативный сценарии спецификации покрыты API-тестами (`*ApiTest`) и тестами страниц.
- Соседний сценарий не сломан: изменение не ломает существующие проверки.
- Новое поведение проверяется на реальном HTTP и чистой БД в памяти, как остальные тесты.

## Объём и процесс

- Изменение не выходит за согласованную спецификацию и тикеты. Если спецификация или комментарий согласования недоступны, отметь это в ревью.
- PR заполнен по шаблону: связанные issues, что изменено, проверки (команды, ссылки на CI, проверенный head SHA), риск, откат.
- Коммиты — по Conventional Commits; коммит реализации ссылается на тикет в конце заголовка.

## Формат замечания

Для каждого подтверждённого дефекта: файл и строка, при каком условии проявляется, к какому последствию приводит. Без предположений и общих советов. Вывод линтера не повторяем.
